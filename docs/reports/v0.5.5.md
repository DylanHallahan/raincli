## R2 in detail: send in place (§20.2, §20.6 M2, M4, L4, L5)
**Branch:** web-builder's `ea0dee8`, on `feat/v055-ui`. No routing changes.

### What changed
- **In a conversation,** the composer sends without a page load. The message is in the thread at once with its delivery trail, and the composer clears. The conversation list's preview and order update straight away, and later states arrive with the 5 s poll.
- **New message** (a new conversation, N1) still posts the classic form. It belongs to R1, which is frozen.
- **The endpoint:** `POST /app/send`, app mode with CSRF.
  - **Fields:** `conversation_id`, `message_id`, `body`, `in_reply_to` and `files`.
  - **Success:** `200 {conversation_id, id, seq, message_html, duplicate}`, with `Cache-Control: no-store`. A website session gets a 404.
  - **The fragment** is the same `app_mode/_message.html` that `/app/live` renders, byte for byte.
- **One merge path (L4):** the client hands the fragment to `live.js`'s own merge by id (`rcLive.merge`).
  - It is skipped if `#m-<id>` is already there, inserted in `seq` order and animated once.
  - The viewer's own message scrolls into view, and an immediate poll follows.
- **No banner:** app mode never shows "Message stored on the server.". Its no-JavaScript form send now redirects without `?notice=sent`. The website keeps its banner.
- **Uploads:** `/app/send` takes attachments like the form send, up to 2 MiB.
  - **Changed:** the app's upload path (`web/middleware.py`) and the Nginx `location` in `deploy/raincli/nginx/raincli.com.conf`.
  - **Deploy step:** reinstall and reload the Nginx conf with this release. Until then, any attachment over 64 KiB is refused by Nginx.
- **Scripts (M4):** `static/app-send.js`, app mode only, loaded by `base_app.html` after `app-mode.js`. Its submit listener sits on the form and calls `preventDefault()`, and `app.js` skips `defaultPrevented` and `form[data-send-in-place]` submits.
- **A reply** sends in place too. Afterwards the composer goes back to the conversation's recipient, as a page load would.

### The message id, replays and conflicts (M2)
- **One id per draft:** `crypto.randomUUID()`, kept across retries.
  - **A new id:** after a success, and after a definite rejection (any 4xx other than 429).
  - **The same id:** after a network error, a 5xx, a 429 or a reply that isn't JSON (the outcome is unknown).
- **A replay** (a stored id with the same content) returns `200 … duplicate: true`. It is answered **before** the per-user rate limit is checked, so a retry never hits the limit.
- **An edited retry** (a stored id with different content) returns `409 id_conflict`. The reply carries the stored message's fragment and "Your earlier version was already sent.".
  - The client inserts the earlier version, shows that line, and keeps the edited draft under a new id.
  - The fragment comes back only when the stored message is the viewer's own and in a conversation they can see; otherwise the reply is just the error.

### Errors (L5)
- **The shape:** every failure is `{error: {code, message}}` with its HTTP status:
  - 403 `forbidden`: CSRF or the session;
  - 404 `not_found`;
  - 400 `invalid` and the service's other codes;
  - 409 `id_conflict`;
  - 413 `too_large`, including the middleware's own;
  - 429 `rate_limited` or `inbox_full`, with `retry_after`.
- **The client** shows one inline `role="status"` line above the box: the server's message, or "Couldn't send. Check your connection and try again." for anything else. The draft and the chosen file names stay until a send succeeds.
